# AI coach

## Why it is shaped this way
Everything the app knows about a person already exists as typed, deterministic data: scored days, ranked gaps, week comparisons, best sets, weight trend, recalibration status. The coach's job is to put all of that at the model's hand and let a person ask anything, in plain words, on a phone. What makes it trustworthy is the same four things as the estimator: fast, consistent, honest about what it looked at, and easy to act on or correct. So:

- **One agent, many tools, no handoffs.** A specialist-per-domain design would cost a round trip per handoff on a phone and split one person's context in two. The specialists are the deterministic functions in `packages/shared` behind the tools. Split into agents only if the prompt or the tool list stops fitting; say so in D41 first.
- **Pre-brief, then tools.** Every turn starts with a compact briefing built in code (profile, targets, today so far, this week, gym week, weight trend, recalibration status, open gaps). Most questions need no tool call; the model reaches for a tool only to drill down (one day, one lift, a month, a food search).
- **The coach never writes.** It drafts: an estimate to log, a target pin to apply, a workout to start, a meal to save, a note to remember (slice 11b). Each comes back as a card the person confirms with a tap, and the confirm goes through the existing endpoint (`POST /log/entries`, `PATCH /targets/overrides`, the session screen's draft store, `POST /meals`, `POST /coach/notes`); the coach's own API only records the card's state afterwards. Non-negotiable 2 holds: AI never sets targets, and no model output reaches a table without a human tap and a zod parse.
- **Numbers come from tools, never from memory.** The prompt forbids numbers that are not in the briefing or a tool result. The smoke test traces every number in the answer back to the data it was given.

## Contract
- **SDK**: the `openai` package already installed (7.x). **API**: Responses, `client.responses.create` with `tools` built by `zodResponsesFunction` (strict function tools from zod; every field required, optionals as `| null`, `additionalProperties: false`), `parallel_tool_calls: true`, `store: false`, `include: ['reasoning.encrypted_content']` so replayed turns keep their reasoning items. The tool loop lives in `apps/api/src/ai/coach/agent.ts`: at most `COACH_MAX_TOOL_ROUNDS` (6) model rounds per turn; each round is one `ai_calls` row with purpose `coach`.
- **Model**: `OPENAI_COACH_MODEL`, defaulting to `OPENAI_MODEL` (D6 one strong model; the override exists so the owner can try a cheaper tier for chat without touching estimation). Reasoning effort `low`; the briefing does the thinking.
- **State**: threads and messages live in our Postgres (`coach_threads`, `coach_messages`), under the one-year retention (D27), inside the export (D24) and the cascade delete. Each turn replays the thread as `input`: the earlier turns as plain user and assistant messages (`replayHistory` in `agent.ts`), the last `COACH_REPLAY_TURNS` (12) in full and older ones cut to one line of `COACH_SUMMARY_CHARS` (160). Function calls, their outputs and reasoning items are **not** replayed across turns: the API refuses a replayed `function_call` without the reasoning item that preceded it, and carrying both costs input tokens on every later turn; a follow-up re-reads a lift or a day through a tool. Within one turn the rounds do carry the model's output items (`toResponseInputItems`) with `include: ['reasoning.encrypted_content']` on reasoning models. OpenAI's `previous_response_id` and Conversations API are not used: they need `store: true` and keep the person's data at OpenAI (D41 option B). A thread is capped at `COACH_MAX_TURNS` (40) turns; after that the composer offers "New chat".
- **Streaming**: `POST /api/v1/coach/threads/:id/messages` answers `text/event-stream`. Events, in order: zero or more `status` (`{ tool, text }`, emitted when a function call item completes, before the tool runs), `card` (`{ card }`, the moment a draft tool returns, validated against `coachCardSchema`) and `delta` (`{ text }`), then one `done` whose data is the `CoachTurnResponse` (`thread`, `user`, `assistant` with its `cards`; a failed turn still ends in `done` with `assistant.error` set and the failure copy as its text), or one `error` only when nothing could be stored. The browser reads it with `fetch` and a `ReadableStream` (`features/coach/api.ts`; EventSource cannot POST). `?stream=false` returns the same `CoachTurnResponse` as JSON for tests and the smoke script. Before anything is stored the route answers plain JSON errors: 400 for an empty or over-long message, 503 `ai_unavailable` with no key, 409 `conflict` at 40 turns, 429 `ai_cap_reached` at the daily cap.
- **Server only.** The key never reaches the browser. The web app calls `/api/v1/coach/*`. Threads are scoped by `user_id` from the session; every tool receives `userId` from the request, never from the model.
- **Consent** (D25): the coach shows `AiConsent` until AI features are allowed, and its copy names what the coach adds to what is sent: the food log for the days it looks at, workouts and weigh-ins. The weekly-review and estimate flows are unchanged.
- **The daily brief** (slice 11c): one line at the top of Today in each half, built by `brief.ts`. `draftBrief(inputs, half)` turns the same `BriefingInputs` the coach reads (eaten food only: a day holding nothing but plans is still an empty day) into labelled FACTS lines and the app's own sentence (food: the furthest-behind of energy and protein with what is left and the main meals still "to go" by the local hour, breakfast until 11, lunch until 15, dinner until 21; gym: sessions done of planned this week, today's session or the last one with its top lift on the person's "best" basis, the week-on-week gain). `getBrief` returns the day's cached row (`coach_briefs`, one per person, half and local day) or asks the model (purpose `brief`, the coach's model, `BRIEF_SYSTEM_PROMPT`, Structured Outputs `{ sentence }`) to say the sentence better; `acceptableSentence` keeps the model's line only when every number in it is one of the facts' and it fits `COACH_BRIEF_MAX_CHARS` (160), else the app's own line is shown and nothing is stored. With nothing logged (or no session in two weeks) the line is an invitation, never sent to the model and never cached, so it changes as soon as something is logged. No key, the daily call cap or a failed call also fall back to the app's own line. `POST /coach/brief { half }`; `POST /coach/threads { brief: half }` opens (or reuses, while unanswered) a chat whose first message is the line as an assistant message, so the reply is answered in context. `briefModel.override` is the test seam.
- **The weekly review reads the briefing.** `weekly-review.ts` composes its prompt from `personLines`, `targetLines` and `weekLines(stats, today, prefs, 'full')` exported by `briefing.ts`, so the review and the coach quote the same numbers, rounding and verdict words.
- **The owner's cost view** (slice 11c, D42): `GET /api/v1/ai/costs` (`apps/api/src/ai/costs.ts`) folds `ai_calls` of the last 30 days by person and purpose; answered only for the account whose email matches `OWNER_EMAIL` (`auth/owner.ts`, also `owner` on `/me`), 404 for everyone else.
- **Notes** (slice 11b, D41 memory option A): `coach_notes` holds the lines the person confirmed from a `note` card; `GET/POST /coach/notes`, `DELETE /coach/notes/:id`; at most `COACH_MAX_NOTES` (30) of `COACH_NOTE_MAX_CHARS` (200) each, since every note goes into every briefing. Kept until deleted (not under the dated retention), in the export as `coachNotes` (schema 5), cascade from `users`. Coach > Notes (`/coach/notes`, reached from the chat list) lists and deletes them.

## The tools
Full catalogue with argument and result shapes in `references/tools.md`. Rules:
1. **Read tools wrap existing services.** `stats-service`, `log-service`, `workouts-service`, `weight-service`, `targets-service`, `recalibration-service`, `foods-service`, `saved-meals-service`. A tool never runs SQL of its own; if a query is missing, add it to the service with a test.
2. **Results are compact and labelled.** Round as the screens do (`fmt` in the weekly review), name units in the field labels, cap lists (20 entries, 20 sessions), and never return a raw row. Token cost is per turn, and the result is replayed on every later turn of the thread.
3. **Days are the user's local day.** Tools take `YYYY-MM-DD`; "today" is resolved in code from `profiles.timezone` and stated in the briefing. The model never computes a date from server time.
4. **Draft tools return cards, not writes.** A draft tool's `run` returns a `DraftResult` (`{ card, summary }`, `tools/types.ts`): the agent validates the card, keeps it for the stored message, emits it as a `card` event, and sends the model `{ card_id, ...summary }` (words and rounded numbers, never the card's payload, which would be replayed on every later turn). `draft_food_log` runs the estimator (`estimate.ts`, same cap and foods memory; the cap error goes back to the model as its message) and returns an `estimate` card; `draft_target_change` dry-runs the pin exactly as `setOverrides` would (`checkOverride` on the engine's entry, `computeTargets` with the new overrides) and returns a `target_change` card with before, after, every target that moved and the floor or range warning, or `{ refused, reason, floor }` with no card for a value under the floor; `draft_workout` matches each exercise to the catalogue (id, exact name, then a used partial match), carries the plan and last time's sets (the latest session where the exercise was done, `lastDoneSession`, so one where it was skipped is passed over), and names what did not match; `draft_meal` builds `SavedMealItem`s from library foods (ids from `search_my_foods` only; another person's id reads as missing); `remember_note` returns the line. A card carries `id`, `kind`, `state` (`drafted` → `confirmed` or `dismissed`, set once through `PATCH /coach/threads/:id/cards/:cardId` after the person's action) and its payload (`packages/shared/src/coach/cards.ts`). The client renders each with the existing component and the confirm hits the existing endpoint.
5. **Honest emptiness.** A tool with nothing to show returns `{ empty: true, reason }` ("no entries on 2026-10-30"); the model says so rather than guessing.

## Prompt rules (and why)
1. **Second person, plain, specific, short.** Phone screen: lead with the answer, then one reason, then one next step. Under 120 words unless asked for detail.
2. **Quote numbers as given**, with units, from the briefing or a tool result; never invent a number, a day, a food or a set. If the data is not there, say what you would need. Days are said as the app prints them ("Tue 27 Oct"), never as ISO digits, which are for tool arguments; the TODAY lines spell out what is left ("105 g left") so the model quotes rather than subtracts; the briefing holds totals, so what someone ate (today included) comes from `get_day_food`.
3. **Targets are the engine's.** Explain them from their `reason` lines; propose changes only as a `draft_target_change` card and say the person decides. Never suggest going under the safety floors (`nutrition-engine` skill).
3a. **Draft, then describe, never claim.** When asked to log, change, plan, save or remember, the model calls the draft tool, describes the card in a sentence or two and says the person confirms with the button. It never says something is logged, applied, started, saved or remembered, and never drafts what was not asked for. Confirmed notes in the briefing are used without being asked and not re-drafted.
3b. **Planned is not eaten (D43).** Plans are in no total. The briefing lists today's on one line under TODAY SO FAR, `get_day_food` returns them as `planned_not_eaten` and reads tomorrow, which holds nothing else. The model may say where the day would land if a plan is eaten and never says it was eaten. It cannot draft a plan: `draft_food_log` refuses a future day and tells it to draft for today, and the person picks Planned or Tomorrow on the card.
4. **No medical advice, no diagnosis, no supplements as treatment.** Point to a professional for pain, illness, disordered eating signals or pregnancy.
5. **Respect the diet pattern, allergies, dislikes and preferences** in every food suggestion; the briefing lists them. Quietly: the model never names an allergy or a dislike in a suggestion ("without shellfish" reads oddly and trips the smoke's conflict check).
6. **Say what you looked at** when a tool was used ("Looking at your last 5 squat sessions"), so the person can tell data from opinion.
7. **Goal-aware.** The day-met rule for the person's goal is stated in the briefing in words (as the weekly review does), and an uncapped energy target is explained as a floor (D40).
8. **Training day awareness.** The briefing says whether today has a session and what the week's plan is (`training_days_per_week`), so "what should I eat tonight" can account for it.

## Flow for one turn
1. Validate the message (trim, cap at 1,000 characters, reject empty). Check consent is implied by the call (the web app gates it); check the key is configured, the thread length cap, and the turn cap (`AI_COACH_DAILY_TURN_CAP`, default 60 turns per local day, counted from `coach_messages` with role `user` since the person's local midnight).
2. Store the user message (the thread's `turns` goes up and its title is set from the first message). Build the briefing from the services (`loadBriefingInputs`, one `Promise.all`; about 1,500 tokens).
3. `input` = one system message (prompt + briefing), the earlier turns as messages (the last 12 in full, older ones cut to one line), the new user message.
4. Loop, at most `COACH_MAX_TOOL_ROUNDS` (6) rounds: call the model with every tool, streaming; forward each `response.output_text.delta` as a `delta`; on each completed `function_call` item emit a `status` with the tool's own status line; log the round to `ai_calls` (usage from `response.completed`; `error` set to `incomplete: max_output_tokens` when cut). No function calls: done. Otherwise append the round's output items and run the calls in parallel: parse the arguments with the tool's zod schema (a failure goes back as `{ error: "arguments rejected: ..." }`, an unknown name as `{ error: "no tool called ..." }`, a thrown tool as `{ error: "that lookup failed; answer without it" }`), cap the output at 12,000 characters, append `function_call_output`. After the sixth round with calls still coming, one more call with `tools: []`, `tool_choice: 'none'` and a developer line asking for the answer from what it has.
5. The answer is the text of every round joined by a blank line (a round that talks before calling a tool keeps its words).
6. Store the assistant message with its text, cards (each `drafted`), the tool trail (`name`, parsed `arguments`, the status line as `summary`, `ms`, `ok`) and the `ai_calls` ids. Emit `done` with the stored user and assistant messages and the thread. A tool that throws an `AppError` (the estimator's cap, a validation refusal) goes back to the model as that message with "tell the person in your own words"; any other throw as "that lookup failed".
7. On any failure after the user message was stored, the turn resolves with the failure copy as its text and `error` set (one transient retry per round before anything streamed); the assistant message is stored like any other, `done` carries it, and the thread shows "The coach is unavailable right now" with Try again, which re-sends the question.

## Cost and abuse guards
Per-user daily turn cap separate from the estimator's call cap (both count in `ai_calls`); round cap per turn; thread turn cap; message length cap; tool result size caps; `max_output_tokens` 700 on answers. The briefing is rebuilt each turn rather than cached so it never goes stale, which is the main token cost; keep it compact. Every round logs tokens, so `ai_calls` grouped by purpose and user is the bill.

## Failure copy
"The coach is unavailable right now. Your question is kept; try again in a moment." Never show raw errors; log them.

## Screens
`/coach` opens the most recent chat (or the empty state), `/coach/new` a fresh one, `/coach/:id` that chat, `/coach/threads` the list (with a Notes row at the top), `/coach/notes` the notes. A card sits under the coach's bubble at full width: the estimate card is the quick-add review (items, meal and day, "Add to breakfast", Add to meals); the target card shows before → after with every target that moves, the reason and the floor line, and Apply; the workout card lists each exercise's planned sets with last time's beside them and Start, which opens the session filled in; the meal card lists the ingredients and totals with "Save to meals"; the note card shows the line with Remember. Every card has Dismiss. Once acted on the buttons give way to a chip (Logged, Applied, Started, Saved, Remembered, Dismissed) and that state survives a reload. While the answer is still streaming a card shows "Drafting…" and holds its buttons until the turn is stored. Offline the confirm reads "(offline)" and is disabled, except Start, which needs no network. The screen is pushed (back goes to the half's Today) with the clock icon on the right for the list; it uses `AppShell`'s `footer` slot for the composer and `hide-tabs`, so the tab bar is gone and the composer rides above the keyboard. The sparkles `CoachButton` sits in the header-right slot of Today and Week in both halves (Meals and Workouts keep their "+", the column holds one icon) and a Coach row sits under You. The consent card (`AiConsent` with `also`) comes before anything else; Settings > AI off brings it back. The brief sits on Today (both halves, today only, under the status line) as an accent-tinted full-width button: sparkles, the sentence, a chevron; a one-line skeleton while it loads, nothing at all before consent or when it cannot be fetched, disabled offline. Its query key (`coachBriefKey(half)`) is dropped by every log and session write so an empty day's invitation gives way to the real line.

## Testing
- **Unit**: the briefing builder against Finn's and Tess's seeded weeks (and the NOTES section); each tool against real Postgres (scoping: a tool asked about another user's id returns empty); the draft tools (the target dry run against `computeTargets`, the floor refusal, last time's sets on the workout card, the meal's snapshot numbers, the note, the estimator's cap); the loop with a fake client that returns scripted function calls (round cap, bad arguments, parallel calls, streaming events in order, a `card` event before the deltas, an `AppError` as words); the routes (cards stored and reopened, state set once and scoped, notes kept, capped, deleted and exported).
- **Brief**: `brief.test.ts` against real Postgres: the food and gym drafts from the seeded data (numbers as the Today tiles print them, every number traceable to the facts), the invitations on an empty day, `acceptableSentence`, the once-a-day cache, an invented number refused and not stored, no model call on an empty day, without a key or at the cap, the chat a brief opens (first message, reuse while unanswered, hidden from the list, replayed to the model), export and retention, and the cost view (404 until `OWNER_EMAIL` names the account, then the grouped rows). `pnpm ai:smoke:brief [--only finn|tess] [--fresh]` prints the facts, the app's own line and the model's for both halves with tokens and latency and the number check.
- **Smoke** (`pnpm ai:smoke:coach [--only finn|tess] [--question N]`, not in CI; `pnpm db:seed` first, `DATABASE_URL` on the shell, and make sure the shell does not export a stale `OPENAI_API_KEY`, which wins over `.env`): the canonical questions in `references/tools.md` against the live model as Finn and Tess through `runTurn` (no thread is stored and no card is confirmed, only `ai_calls` rows; question 6 spends one estimator call); prints each answer, the tools used, the cards drafted (one line each), rounds, tokens and latency; re-runs the recorded read tools (not the draft tools: the estimator would be spent again and answer differently; the cards carry what the model was told, with the estimate card's whole-number items and totals) and checks that every number in the answer appears in the briefing, the question, a tool result or a card, that no word matches the allergies or dislikes (shellfish expands to prawn, crab and so on), and that questions 5 to 7 and 11 drafted the expected card kind (5 may instead reason against a change). Ends with a markdown table to paste into the slice report. Run it on a clean `pnpm db:seed` (delete Finn and Tess first if a walk pinned a target or left a note on them: the model rightly declines to re-draft an existing note). Expect 2 to 5 s per answer without a tool, 9 to 15 s with a draft, about 5,500 input tokens a turn; the first live table (2026-11-03) is in PLAN.md under slice 11a.
- **Walking without a key**: the model is the only thing a walk cannot run; a throwaway script that sets `coachModel.override` to a question-keyed fake (and `briefModel.override` to a writer that rephrases the app's own sentence) and serves `createApp()` lets the draft tools and every card screen run for real against the local database (the estimate card excepted: its tool calls the estimator, so seed a message carrying a card built from the `__fixtures__` estimates).
- **Walk**: the `/coach` screen at 360, 390 and 430 wide, dark and light, with the keyboard open (the composer stays above it, the list scrolls under), a streamed answer, each card confirmed through its own screen (Targets reads "Set by you", the session opens filled in with last time beside each set, the note under Coach > Notes and in the next briefing, the entries on the day log), a card dismissed and still dismissed after a reload, offline (composer and confirms disabled with a line), consent not yet given.
